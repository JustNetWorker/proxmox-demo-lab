# Развёртывание учебного стенда в Proxmox VE

Проект создаёт учебный стенд из восьми виртуальных машин: **ISP, HQ-RTR, HQ-SW, HQ-SRV, HQ-CLI, BR-RTR, BR-FW и BR-SRV**. Готовые диски qcow2 скачиваются с Google Drive и импортируются в Proxmox. Скрипт назначает названия ВМ, процессоры, оперативную память, контроллеры дисков и сетевые адаптеры, а также создаёт мосты для соединения машин.

После завершения все ВМ остаются **выключенными**. Повторная установка ОС из ISO не требуется.

**Область автоматизации:** создание ВМ и их виртуального оборудования. IP-адреса, VLAN, маршруты, DNS, DHCP, VPN и правила межсетевого экрана внутри гостевых ОС скрипт не настраивает. Развёртывание базовых образов не означает выполнение первого модуля демонстрационного экзамена.

## Требования

- Узел Proxmox VE на платформе x86-64 с доступом к Shell от `root`.
- Доступ к GitHub, Google Drive и настроенным репозиториям пакетов.
- Активный Linux Bridge для внешнего подключения ISP. По умолчанию скрипт определяет его по IPv4-маршруту узла Proxmox по умолчанию; номер моста значения не имеет.
- Свободный диапазон из восьми VMID и девяти номеров мостов. По умолчанию скрипт подбирает их автоматически.
- Активное хранилище для дисков ВМ; по умолчанию — `local-lvm`.
- Свободное место для скачанных qcow2 и импортированных дисков. Это два отдельных расхода места, если кэш и диски ВМ находятся на одном физическом накопителе.

Одновременный запуск всех машин требует **18 ГиБ ОЗУ для гостей плюс память узла Proxmox**. Для полного стенда рекомендуется выделить не менее 24 ГиБ. При меньшем объёме памяти ВМ следует запускать по отдельности; создание выключенных машин не требует выделения всей их оперативной памяти сразу.

Для тестового Proxmox внутри другой ВМ можно использовать диск 120–150 ГиБ, оставив достаточно места именно в пуле дисков ВМ. Вложенная виртуализация требуется для запуска созданных гостей. Скрипт её не включает.

### Как рассчитывается место

Для `lvmthin` скрипт оценивает записанные блоки образов после распаковки и учитывает отдельный импорт каждой ВМ. К оценке добавляется резерв: **не менее 10 ГиБ или 25% объёма импорта**, в зависимости от того, что больше. Размер сжатого файла qcow2 не равен занимаемому месту в thin pool после импорта.

Для остальных типов хранилищ используется консервативная проверка полной виртуальной ёмкости дисков с запасом. Для текущего набора базовых образов это примерно **340 ГиБ плюс EFI и резерв**.

Перед созданием скрипт выводит доступное место, оценку импорта и резерв. По мере записи данных гостевыми ОС заполнение thin pool растёт; свободное место и `Data%` необходимо контролировать.

## Быстрый запуск

Открыть **узел Proxmox → Shell** и выполнить:

```bash
curl -fSL https://raw.githubusercontent.com/JustNetWorker/proxmox-demo-lab/main/bootstrap.sh -o /root/demo-bootstrap.sh && bash /root/demo-bootstrap.sh --menu
```

| Пункт меню | Действие |
|---|---|
| `1` | Показать план: имена, ресурсы и подключения. Образы не скачиваются, ВМ не создаются. |
| `2` | Скачать образы, проверить их и создать стенд. |
| `3` | Изменить номера, хранилище и внешнее подключение; `auto` оставляет автоматический подбор. |
| `4` | Выбрать профиль: базовые ОС или стенд второго модуля. |
| `5` | Проверить ВМ выбранного стенда: состояние, диски, карты, мосты и ресурсы. |
| `6` | Показать файлы кэша и очистить их после подтверждения. |
| `7` | Показать выбранный стенд и удалить его ВМ, подключённые диски и собственные мосты после подтверждения. |
| `8` | Создать снимки `lab-initial` для выключенных ВМ, если все диски поддерживают снимки. |
| `0` | Завершить работу. |

По умолчанию номера вводить не нужно: скрипт выбирает восемь свободных VMID подряд, начиная поиск с `200`, и девять свободных номеров мостов, начиная с `201`. В пункте **1** можно посмотреть выбранные номера, затем выбрать **2** для создания. Занятые ВМ, контейнеры и мосты пропускаются. Названия машин остаются `ISP`, `HQ-RTR` и т. д.

План и создание проверяют текущее состояние отдельно: если между ними другой процесс занял номера, диапазон при создании может измениться. Точные номера видны перед импортом и в сообщении о завершении. Уже созданный стенд повторный запуск не переименовывает и не продолжает: при `auto` будет создан ещё один стенд на свободном диапазоне.

После создания меню остаётся открытым: можно проверить стенд, сделать снимки или очистить кэш. Для операций со стендом выбирается его журнал `/root/demo-deploy.XXXXXXXX` из показанного списка.

Первый запуск скачивает и импортирует диски; продолжительность зависит от сети и накопителей. Консоль следует оставить открытой до завершения. При наличии `tmux` запуск можно выполнять в его сессии.

### Запуск без меню

Показать план:

```bash
bash /root/demo-bootstrap.sh --deploy-plan
```

Создать стенд:

```bash
bash /root/demo-bootstrap.sh --deploy
```

Для нового узла сначала выполняется команда загрузки `bootstrap.sh` из раздела «Быстрый запуск».

## Параметры

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `--base-id` | `auto` | Подобрать восемь свободных VMID по всему кластеру, включая контейнеры. Можно задать первый номер вручную: `--base-id 300`. |
| `--bridge-base` | `auto` | Подобрать девять свободных номеров мостов с учётом активных интерфейсов и конфигурации сети. Можно указать первый номер: `--bridge-base 301`. |
| `--storage` | `local-lvm` | Хранилище для импортируемых дисков. |
| `--uplink` | `auto` | Определить внешний мост по IPv4-маршруту узла. Можно указать явно, например `--uplink vmbr7`. |
| `--image-dir` | `/var/lib/vz/demo-images` | Каталог кэша скачанных образов. Для профиля `module2` используется подкаталог `module2`. |
| `--profile` | `base` | Базовые ОС; `module2` — стенд второго модуля из отдельных настроенных образов. |

Пример для другого диапазона и хранилища:

```bash
bash /root/demo-bootstrap.sh --deploy-plan --base-id 300 --bridge-base 301 --storage lab-disks --uplink vmbr0
bash /root/demo-bootstrap.sh --deploy --base-id 300 --bridge-base 301 --storage lab-disks --uplink vmbr0
```

`lab-disks` в примере — имя заранее настроенного хранилища. Если используется стандартное `local-lvm`, параметр `--storage` можно опустить.

Пример размещения кэша на другом смонтированном накопителе:

```bash
bash /root/demo-bootstrap.sh --deploy --image-dir /mnt/lab-cache/demo-images
```

Каталог должен находиться на доступной файловой системе с достаточным свободным местом.

## Состав стенда

Номера приведены для свободного узла, где автовыбор даёт VMID 200–207 и мосты vmbr201–vmbr209. Размер диска определяется импортированным образом; существующая большая ёмкость не уменьшается.

| VMID | Имя | Базовый образ | ОЗУ, МиБ | Ядра | Виртуальный диск |
|---|---|---|---|---|---|
| 200 | ISP | ALT JeOS | 1024 | 1 | 32 ГиБ |
| 201 | HQ-RTR | EcoRouter | 2048 | 2 | не менее 10 ГиБ |
| 202 | HQ-SW | ALT JeOS | 1024 | 1 | 32 ГиБ |
| 203 | HQ-SRV | ALT Server | 2048 | 1 | 32 ГиБ |
| 204 | HQ-CLI | ALT Workstation | 2048 | 2 | 32 ГиБ |
| 205 | BR-RTR | EcoRouter | 2048 | 2 | не менее 10 ГиБ |
| 206 | BR-FW | Ideco | 6144 | 4 | 160 ГиБ и отдельный EFI-диск |
| 207 | BR-SRV | ALT Server | 2048 | 1 | 32 ГиБ |

Для всех ВМ используется CPU `host`, один сокет, отключённый ballooning и отключённый автоматический запуск. EcoRouter получает контроллер SATA и карты e1000. ALT — SeaBIOS, VirtIO SCSI и карты VirtIO. Ideco — q35, OVMF, VirtIO SCSI и карты VirtIO; состояние UEFI восстанавливается из отдельного образа.

Если исходный диск EcoRouter меньше 10 ГиБ, скрипт увеличивает виртуальный диск до 10 ГиБ. Разделы и файловые системы внутри гостя автоматически не расширяются.

## Схема сети

### Внешнее подключение ISP

По умолчанию скрипт читает IPv4-маршруты узла Proxmox и выбирает мост маршрута по умолчанию с наименьшей метрикой. К нему подключается **net0 ISP**. Например, при маршруте через `vmbr7` будет выбран `vmbr7`, а не `vmbr0`. Определённое подключение выводится в плане:

```text
Detected host IPv4 uplink: vmbr7 -> ISP net0
```

Если маршрут неоднозначен, отсутствует или проходит через VLAN-интерфейс, VPN либо физическую карту вместо Linux Bridge, скрипт останавливается до создания ВМ. Внешний мост можно выбрать вручную через `--uplink vmbrN`. Автовыбор предназначен для обычной схемы Linux Bridge с внешним шлюзом; он не настраивает NAT хоста, VLAN внешней карты или выдачу дополнительных публичных адресов у провайдера.

Скрипт использует существующий мост вместе с его подключением к физической сети. **IP-адрес и шлюз Proxmox не копируются на другие мосты или в ISP.** В самой ОС ISP внешний интерфейс должен получить собственный адрес, шлюз и DNS по DHCP либо иметь подходящую статическую конфигурацию из образа. Наличие внешнего моста само по себе не настраивает гостевую ОС.

Существующий внешний мост используется только для внешней карты ISP. Новые мосты создаются без IP-адресов узла и без физических портов. Это внутренние соединения стенда; интернет остальных машин требует маршрутизации и NAT внутри ISP и офисных устройств.

В таблицах ниже `uplink` обозначает автоматически найденный или явно указанный внешний мост.

| Мост | Соединение |
|---|---|
| `uplink` | Внешняя сеть — ISP |
| `vmbr201` | ISP — HQ-RTR |
| `vmbr202` | ISP — BR-RTR |
| `vmbr203` | HQ-RTR — HQ-SW |
| `vmbr204` | HQ-SW — HQ-SRV |
| `vmbr205` | HQ-SW — HQ-CLI |
| `vmbr206` | BR-RTR — BR-FW |
| `vmbr207` | BR-FW — BR-SRV |
| `vmbr208` | Служебная карта HQ-RTR |
| `vmbr209` | Служебная карта BR-RTR |

Порядок адаптеров базового профиля:

| ВМ | net0 | net1 | net2 |
|---|---|---|---|
| ISP | uplink | vmbr201 | vmbr202 |
| HQ-RTR | vmbr208 | vmbr201 | vmbr203 |
| HQ-SW | vmbr203 | vmbr204 | vmbr205 |
| HQ-SRV | vmbr204 | — | — |
| HQ-CLI | vmbr205 | — | — |
| BR-RTR | vmbr209 | vmbr202 | vmbr206 |
| BR-FW | vmbr207 | vmbr206 | — |
| BR-SRV | vmbr207 | — | — |

На EcoRouter первая карта предназначена для управления, вторая подключена к ISP, третья — к локальной сети. На BR-FW первая карта подключена к BR-SRV, вторая — к BR-RTR.

Firewall на создаваемых адаптерах выключен. VLAN-теги Proxmox не назначаются. Сопоставление карт с интерфейсами гостевых ОС и настройка VLAN выполняются внутри машин после импорта.

## Профили стенда

**Базовые ОС (`base`)** — текущие установленные ALT, EcoRouter и Ideco. Одни базовые образы используются для нескольких ролей; гостевые настройки модуля не назначаются.

**Стенд второго модуля (`module2`)** — восемь отдельных дисков с сохранёнными настройками первого модуля. Это исходная среда для выполнения второго модуля, а не автоматическое выполнение его заданий. Профиль сохраняет BIOS, тип машины, контроллер и подключение системного диска, UUID, модели, MAC и порядок сетевых карт. VMID и номера внутренних мостов подбираются заново; CPU и ОЗУ назначаются по таблице ресурсов скрипта.

Образы подготавливаются в [отдельной папке Google Drive](https://drive.google.com/drive/folders/1Kfd3wSSBchtk4-ISPV2WnNqs_HopeNY0). Пока в репозитории нет заполненного `module2-images.json`, профиль недоступен для скачивания. Базовые образы сохраняются отдельно. После публикации манифеста bootstrap автоматически загрузит его при выборе профиля; уже существующий локальный манифест не перезаписывается.

Для развёртывания выбрать **4 → 2** в меню, проверить план (**1**) и создать стенд (**2**). Из командной строки:

```bash
bash /root/demo-bootstrap.sh --deploy --profile module2
```

Порядок карт определяется метаданными образов. В настроенной исходной Ideco `net0` подключён к BR-RTR, `net1` — к BR-SRV; это отличается от базового профиля. Исходный ISP и его копию нельзя одновременно запускать на одном внешнем мосту: профиль сохраняет MAC и гостевую DHCP-идентичность.

### Сохранение настроенного стенда

Все восемь ВМ нужно штатно выключить. Экспорт не выключает и не запускает их автоматически. Сначала загрузить компоненты через пункт **1** меню, затем выполнить:

```bash
python3 /root/proxmox-demo-lab/export-module2.py \
  --ids 101,100,104,102,103,108,106,105 \
  --output /var/lib/vz/module2-export
```

Номера здесь — пример. Порядок обязателен: **ISP, HQ-RTR, HQ-SW, HQ-SRV, HQ-CLI, BR-RTR, BR-FW, BR-SRV**. Каталог назначения должен быть новым. Экспорт поддерживает один системный диск на ВМ, схемы мостов `vmbr1`–`vmbr9` из таблицы и отдельный внешний мост ISP. Дополнительные диски, TPM, сетевые VLAN-теги и отложенные изменения требуют отдельной адаптации и отклоняются до сохранения.

Экспорт блокирует запуск машин на время копирования, сохраняет их конфигурации, сжимает диски в самостоятельные qcow2, проверяет структуру каждого файла и сравнивает содержимое с исходным диском. При ошибке уже готовые файлы сохраняются, блокировки снимаются. На файловой системе остаётся резерв 4 ГиБ. История снимков и состояние оперативной памяти не экспортируются.

Если у Ideco нет постоянного EFI-диска, экспорт сохраняет штатный шаблон переменных OVMF, отмечая это в метаданных. Он не выдаётся за сохранённые переменные исходной ВМ. Загрузку восстановленной Ideco необходимо проверить отдельно.

Чтобы опубликовать полученный набор:

1. Загрузить все `.qcow2` в отдельную папку Google Drive и разрешить скачивание по ссылке. Конфигурации `*-config.txt` оставить для восстановления у владельца стенда.
2. В `module2-images.pending.json` заполнить `id` каждого файла из ссылок Drive. Имена, SHA256, размеры и `hardware` уже сформированы экспортом; их необходимо сохранить.
3. Сохранить заполненный файл как `/root/proxmox-demo-lab/module2-images.json` или опубликовать в репозитории. Шаблон [`module2-images.example.json`](module2-images.example.json) показывает формат и оборудование исходного стенда, но не содержит ссылок на готовые загрузки.

Старый `--profile module1` оставлен для совместимости с локальными `module1-images.json` и журналами. В новом меню используется название «Стенд второго модуля».

| Файл | Использование |
|---|---|
| `alt-jeos.qcow2` | ISP и HQ-SW |
| `alt-server.qcow2` | HQ-SRV и BR-SRV |
| `alt-workstation.qcow2` | HQ-CLI |
| `EcoRouterOS.qcow2` | HQ-RTR и BR-RTR |
| `ideco.qcow2` | Основной диск BR-FW |
| `ideco-efi.qcow2` | Состояние UEFI BR-FW |

ID файлов, имена и доступные контрольные суммы находятся в [`images.json`](images.json). Скрипт обращается к отдельным файлам, а не скачивает всю папку. Учётная запись Google для публичных файлов не требуется.

Файл конфигурации Ideco читается как данные: команды из него не выполняются. Основной диск и EFI должны быть экспортированы из одной выключенной ВМ. UUID SMBIOS и MAC net0 сохраняются, а CPU, RAM и подключения назначаются по параметрам скрипта. Лицензия после восстановления проверяется в панели Ideco. Оригинал и его копия с одинаковым MAC не должны одновременно подключаться к одной сети.

Для замены источников необходимо обновить `images.json` и проверить совместимость образов с контроллерами и прошивкой, которые задаёт `deploy.sh`. Замена только ссылки не гарантирует загрузку произвольной ОС.

## После развёртывания

Успешное завершение обозначается строкой:

```text
Finished: VM IDs 200–207. All machines are stopped.
```

При другом `--base-id` в сообщении будет соответствующий диапазон.

1. Проверить наличие восьми ВМ в панели Proxmox и их раздел **Hardware**.
2. Запустить машины по очереди, проверить загрузку ОС через **Console**.
3. Настроить уникальные имена внутри ОС, IP-адреса и необходимые службы.
4. Проверить лицензию Ideco и сопоставление её сетевых интерфейсов.

Название ВМ в панели не изменяет hostname внутри ОС. Пароли остаются такими, как в базовых образах; скрипт их не назначает и не сбрасывает. Данные для входа должны быть известны пользователю базового образа.

Копии общей ALT-базы наследуют системные идентификаторы и SSH host keys. Перед использованием им следует назначить уникальные machine-id и SSH-ключи узла. Автоматическая подготовка гостевых идентификаторов в текущей версии не реализована.

## Управление созданным стендом

Каждый новый запуск сохраняет `lab.json` в своём журнале: узел, профиль, VMID, названия и UUID ВМ, диски, карты и точные добавленные блоки конфигурации мостов. Пункты управления используют этот список. Один только диапазон VMID не считается основанием для удаления.

### Проверка — пункт 5

Выбрать журнал из списка. Проверка показывает состояние каждой ВМ, наличие дисков и активных мостов, блокировки, ресурсы и изменения оборудования относительно журнала. Итог содержит суммарную память и vCPU. Это проверка оборудования; загрузка гостевой ОС, DHCP, интернет и службы первого модуля проверяются отдельно через консоли машин.

### Очистка образов — пункт 6

Сначала выводятся распознанные файлы кэша и их общий размер. Для удаления нужно ввести `CLEAR`. Удаляются образы, их `.demo.json` и частичные `.demo-download` из текущего каталога кэша; неизвестные файлы и сам каталог сохраняются. Символические ссылки отклоняются. Если конфигурация ВМ или контейнера ссылается на диск внутри кэша, очистка не выполняется.

Импортированные диски ВМ находятся в целевом хранилище и сохраняются. Следующее создание потребует повторного скачивания очищенных образов. Пока идёт импорт, очистка блокируется.

### Удаление стенда — пункт 7

Сначала штатно выключить его ВМ и дождаться завершения активных задач. Выбрать журнал и сверить показанные VMID, названия, диски и мосты. Подтверждение: `DELETE demo-deploy.XXXXXXXX`, где имя берётся из выбранного журнала.

Скрипт проверяет метку запуска, UUID, имя, диски и карты; изменение принадлежности или оборудования останавливает удаление. Наличие работающей или заблокированной ВМ также останавливает операцию. Скрипт не использует `skiplock`, принудительное выключение, удаление неупомянутых дисков или глобальную перезапись сети.

Удаляются только зарегистрированные ВМ с их подключёнными дисками, затем собственные мосты с неизменёнными блоками конфигурации. Если мост или диск используется другой ВМ/контейнером, либо на мост добавлен адрес узла или остались активные порты, удаление отклоняется. Кэш, журнал, резервные копии и внешний мост ISP сохраняются. При ошибке операция останавливается, выполненные удаления остаются выполненными; журнал позволяет проверить оставшиеся ресурсы и повторить действие.

**Старые стенды:** если журнал содержит только `created.tsv`, меню предлагает регистрацию. Она требует полного стенда из восьми ВМ, исходного `interfaces.before`, прежних меток запуска и девяти исходных мостов. Показанный список нужно подтвердить строкой `REGISTER demo-deploy.XXXXXXXX`. Регистрация записывает инвентарь без изменения ВМ и сети. При недостаточных данных она отклоняется; произвольные существующие машины не подхватываются.

### Начальные снимки — пункт 8

Для полного стенда из восьми выключенных и незаблокированных ВМ создаются снимки `lab-initial` без сохранения RAM. До первого снимка проверяется поддержка снимков у всех кандидатов через API Proxmox. Уже существующие `lab-initial` не перезаписываются. Если операция прервётся после нескольких ВМ, повторный запуск пропустит их снимки и обработает оставшиеся.

Снимок сохраняет текущее состояние, поэтому для точки возврата к свежему стенду его следует создать до экспериментов. Откат выполняется отдельно в панели **ВМ → Snapshots → lab-initial → Rollback**. Снимки занимают место по мере записи новых данных и не заменяют резервные копии. [Команды снимков Proxmox](https://github.com/proxmox/pve-docs/blob/master/generated/qm.1-synopsis.adoc).

### Управление без меню

```bash
bash /root/demo-bootstrap.sh --manage list
bash /root/demo-bootstrap.sh --manage check --journal /root/demo-deploy.XXXXXXXX
bash /root/demo-bootstrap.sh --manage snapshots --journal /root/demo-deploy.XXXXXXXX
bash /root/demo-bootstrap.sh --manage delete --journal /root/demo-deploy.XXXXXXXX
bash /root/demo-bootstrap.sh --manage clean-cache --image-dir /var/lib/vz/demo-images
```

Вместо `XXXXXXXX` нужно указать точное имя существующего журнала. Для старого стенда сначала выполнить `--manage adopt --journal /root/demo-deploy.XXXXXXXX` и подтвердить регистрацию. Список журналов и проверка не удаляют ресурсы. Операции управления и развёртывание используют общую блокировку.

## Диагностика

Журнал каждого запуска сохраняется в `/root/demo-deploy.XXXXXXXX/deploy.log`. Там же находятся копия конфигурации сети до изменений, сведения о проверенных образах, расчёт места и список созданных ВМ, если создание уже началось.

### Недостаточно места

Сообщение `Not enough disk space` означает, что свободного места в целевом хранилище недостаточно для рассчитанного импорта и резерва.

Проверить состояние:

```bash
pvesm status
lvs -a -o lv_name,lv_size,data_percent,metadata_percent
```

Решения: расширить целевое хранилище или указать другое через `--storage`. Увеличение виртуального диска узла Proxmox само по себе не расширяет раздел, LVM и thin pool. Команды расширения зависят от фактической схемы дисков.

### Google Drive не отдаёт файл

В сообщении указываются имя файла и публичная ссылка. Возможные причины — изменение доступа, ограничение скачиваний Google или временная ошибка соединения. Доступность файла можно проверить в браузере без входа в аккаунт.

После устранения причины повторить:

```bash
bash /root/demo-bootstrap.sh --deploy
```

Завершённые скачивания сохраняются и проверяются перед повторным использованием; частичные скачивания возобновляются, если это поддерживается источником.

Для `ideco-efi.qcow2` в манифесте опубликованы размер и SHA256. Его можно скопировать вручную в каталог кэша с точным именем `ideco-efi.qcow2`; скрипт примет файл только при совпадении опубликованной контрольной суммы. Это также относится к другим файлам, если для них в манифесте задан SHA256.

Локальные контрольные суммы защищают от изменения кэша после скачивания. Они не являются подписью производителя ОС.

### Занятые VMID или мосты

При `auto` занятые VMID во всём кластере и уже настроенные мосты пропускаются. Если номера заданы вручную через `--base-id` и `--bridge-base`, конфликт останавливает запуск до скачивания и создания ВМ. Существующие машины и мосты не заменяются.

### Ошибка после начала создания ВМ

Новые ВМ и сетевые изменения сохраняются для диагностики. При ошибке развёртывания автоматическое удаление и откат не выполняются; удаление выбирается отдельно в меню после проверки журнала. Перед повторным запуском необходимо проверить журнал и состояние частично созданного стенда. Повторный запуск с явно заданным занятым диапазоном остановится. При `auto` будет выбран другой диапазон и создан новый стенд; автоматическое продолжение частичного импорта не реализовано. Чтобы завершить прежний стенд, сначала нужно выяснить причину ошибки и состояние его ВМ.

### Отложенные изменения сети Proxmox

При наличии `/etc/network/interfaces.new` запуск останавливается. Перед развёртыванием необходимо применить или отменить ожидающие изменения сети в Proxmox.

## Режим для существующих ВМ

Отдельный режим подключает адаптеры уже существующего стенда. Он использует [`connect-adapters.sh`](connect-adapters.sh) и [`machines.tsv`](machines.tsv), не скачивает образы и не создаёт машины.

```bash
bash /root/demo-bootstrap.sh --plan
bash /root/demo-bootstrap.sh --apply
```

`--plan` показывает изменения, `--apply` применяет их. **Эти параметры относятся к адаптерам существующих ВМ; для нового стенда используются `--deploy-plan` и `--deploy`.**

Перед применением необходимо проверить локальную таблицу `machines.tsv`, названия и номера ВМ, порядок карт и существующие мосты. ВМ должны быть штатно выключены, без блокировок и отложенных изменений; Suspend не заменяет выключение. Скрипт не выключает их автоматически.

При первой записи создаётся каталог `/root/demo-adapters-backup.XXXXXXXX` с конфигурациями и `restore-nics.sh` для возврата изменённых карт. Повторные запуски bootstrap сохраняют локальную таблицу VMID, чтобы не перезаписать пользовательские изменения.

## Статус проверки

Проверены синтаксис и формирование плана; пройдено 49 локальных тестов с имитацией команд Proxmox. Тесты охватывают импорт основного и EFI-диска, назначение ресурсов, отказ до изменений при занятых VMID и недостатке места, расчёт для thin pool, обработку ошибок Google Drive и проверку локальной копии по SHA256, выбор внешнего моста с ненулевым номером, приоритет маршрутов, ручной выбор и отказ при неоднозначном или неподходящем маршруте, автоматический подбор свободных диапазонов, учёт неактивных мостов из конфигурации и передачу настроек из меню. Дополнительно проверены перенос контроллеров и порядка карт настроенного профиля, экспорт выключенных машин с проверкой содержимого и снятие блокировок при ошибках, импорт отдельных дисков профиля модуля, запись инвентаря, регистрация старого журнала, удаление только зарегистрированных ресурсов, отказ при подмене VMID/дисков, изменённом мосте, чужих ссылках на диски, запущенных ВМ и отмене подтверждения, очистка кэша с сохранением неизвестных файлов и создание снимков без памяти.

По результатам пользовательских проверок подтверждены:

- создание всех восьми ВМ на тестовом узле Proxmox;
- загрузка всех восьми гостевых ОС и обнаружение их сетевых адаптеров на основном узле;
- доступ в интернет из ISP после ручной настройки DHCP внутри гостевой ОС. Внешняя карта ISP была подключена к существующему `vmbr0`.

Автоматическая настройка DHCP в гостевом образе не выполняется. Новые автовыбор внешнего моста, подбор номеров, управление стендом и импорт отдельного профиля модуля проверены локальными тестами. Проверка этих изменений на реальном узле пока не подтверждена. Набор «Стенд второго модуля» сохраняется отдельно; публикация файлов и проверка загрузки восстановленных ВМ ещё не завершены. Проверка загрузки ВМ и наличия карт не подтверждает настройку внутренней адресации, маршрутизации и служб первого модуля.

При сообщении об ошибке следует приложить версию Proxmox, команду запуска, сообщение об ошибке и соответствующий фрагмент журнала без учётных данных.
