# Развёртывание учебного стенда в Proxmox VE

Проект создаёт учебный стенд из восьми виртуальных машин: **ISP, HQ-RTR, HQ-SW, HQ-SRV, HQ-CLI, BR-RTR, BR-FW и BR-SRV**. Готовые диски qcow2 скачиваются с Google Drive и импортируются в Proxmox. Скрипт назначает названия ВМ, процессоры, оперативную память, контроллеры дисков и сетевые адаптеры, а также создаёт мосты для соединения машин.

После завершения все ВМ остаются **выключенными**. Повторная установка ОС из ISO не требуется.

**Область автоматизации:** создание ВМ и их виртуального оборудования. IP-адреса, VLAN, маршруты, DNS, DHCP, VPN и правила межсетевого экрана внутри гостевых ОС скрипт не настраивает. Развёртывание базовых образов не означает выполнение первого модуля демонстрационного экзамена.

## Требования

- Узел Proxmox VE на платформе x86-64 с доступом к Shell от `root`.
- Доступ к GitHub, Google Drive и настроенным репозиториям пакетов.
- Активный Linux Bridge для внешнего подключения ISP; по умолчанию — `vmbr0`.
- Свободные номера ВМ **200–207** и мостов **vmbr201–vmbr209** либо другой диапазон, указанный при запуске.
- Активное хранилище для дисков ВМ; по умолчанию — `local-lvm`.
- Свободное место для скачанных qcow2 и импортированных дисков. Это два отдельных расхода места, если кэш и диски ВМ находятся на одном физическом накопителе.

Одновременный запуск всех машин требует **18 ГиБ ОЗУ для гостей плюс память узла Proxmox**. Для полного стенда рекомендуется выделить не менее 24 ГиБ. При меньшем объёме памяти ВМ следует запускать по отдельности; создание выключенных машин не требует выделения всей их оперативной памяти сразу.

Для тестового Proxmox внутри другой ВМ можно использовать диск 120–150 ГиБ, оставив достаточно места именно в пуле дисков ВМ. Вложенная виртуализация требуется для запуска созданных гостей. Скрипт её не включает.

### Как рассчитывается место

Для `lvmthin` скрипт оценивает записанные блоки образов после распаковки и учитывает отдельный импорт каждой ВМ. К оценке добавляется резерв: **не менее 10 ГиБ или 25% объёма импорта**, в зависимости от того, что больше. Размер сжатого файла qcow2 не равен занимаемому месту в thin pool после импорта.

Для остальных типов хранилищ используется консервативная проверка полной виртуальной ёмкости дисков с запасом. Для текущего набора базовых образов это примерно **340 ГиБ плюс EFI и резерв**.

Перед созданием скрипт выводит доступное место, оценку импорта и резерв. По мере записи данных гостевыми ОС заполнение thin pool растёт; свободное место и `Data%` необходимо контролировать.

## Быстрый запуск

Открыть **узел Proxmox → Shell** и выполнить:

```bash
curl -fSL https://raw.githubusercontent.com/JustNetWorker/proxmox-demo-lab/main/bootstrap.sh -o /root/demo-bootstrap.sh && bash /root/demo-bootstrap.sh --menu
```

| Пункт меню | Действие |
|---|---|
| `1` | Показать план: имена, ресурсы и подключения. Образы не скачиваются, ВМ не создаются. |
| `2` | Скачать образы, проверить их и создать стенд. |
| `0` | Завершить работу. |

Первый запуск скачивает и импортирует диски; продолжительность зависит от сети и накопителей. Консоль следует оставить открытой до завершения. При наличии `tmux` запуск можно выполнять в его сессии.

### Запуск без меню

Показать план:

```bash
bash /root/demo-bootstrap.sh --deploy-plan
```

Создать стенд:

```bash
bash /root/demo-bootstrap.sh --deploy
```

Для нового узла сначала выполняется команда загрузки `bootstrap.sh` из раздела «Быстрый запуск».

## Параметры

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `--base-id` | `200` | Первый номер ВМ; используются восемь последовательных VMID. |
| `--bridge-base` | `201` | Первый номер нового моста; используются девять последовательных номеров. |
| `--storage` | `local-lvm` | Хранилище для импортируемых дисков. |
| `--uplink` | `vmbr0` | Существующий активный мост для внешней карты ISP. |
| `--image-dir` | `/var/lib/vz/demo-images` | Каталог кэша скачанных образов. |

Пример для другого диапазона и хранилища:

```bash
bash /root/demo-bootstrap.sh --deploy-plan --base-id 300 --bridge-base 301 --storage lab-disks --uplink vmbr0
bash /root/demo-bootstrap.sh --deploy --base-id 300 --bridge-base 301 --storage lab-disks --uplink vmbr0
```

`lab-disks` в примере — имя заранее настроенного хранилища. Если используется стандартное `local-lvm`, параметр `--storage` можно опустить.

Пример размещения кэша на другом смонтированном накопителе:

```bash
bash /root/demo-bootstrap.sh --deploy --image-dir /mnt/lab-cache/demo-images
```

Каталог должен находиться на доступной файловой системе с достаточным свободным местом.

## Состав стенда

Номера приведены для параметров по умолчанию. Размер диска определяется импортированным образом; существующая большая ёмкость не уменьшается.

| VMID | Имя | Базовый образ | ОЗУ, МиБ | Ядра | Виртуальный диск |
|---|---|---|---|---|---|
| 200 | ISP | ALT JeOS | 1024 | 1 | 32 ГиБ |
| 201 | HQ-RTR | EcoRouter | 2048 | 2 | не менее 10 ГиБ |
| 202 | HQ-SW | ALT JeOS | 1024 | 1 | 32 ГиБ |
| 203 | HQ-SRV | ALT Server | 2048 | 1 | 32 ГиБ |
| 204 | HQ-CLI | ALT Workstation | 2048 | 2 | 32 ГиБ |
| 205 | BR-RTR | EcoRouter | 2048 | 2 | не менее 10 ГиБ |
| 206 | BR-FW | Ideco | 6144 | 4 | 160 ГиБ и отдельный EFI-диск |
| 207 | BR-SRV | ALT Server | 2048 | 1 | 32 ГиБ |

Для всех ВМ используется CPU `host`, один сокет, отключённый ballooning и отключённый автоматический запуск. EcoRouter получает контроллер SATA и карты e1000. ALT — SeaBIOS, VirtIO SCSI и карты VirtIO. Ideco — q35, OVMF, VirtIO SCSI и карты VirtIO; состояние UEFI восстанавливается из отдельного образа.

Если исходный диск EcoRouter меньше 10 ГиБ, скрипт увеличивает виртуальный диск до 10 ГиБ. Разделы и файловые системы внутри гостя автоматически не расширяются.

## Схема сети

Существующий внешний мост используется только для внешней карты ISP. Новые мосты создаются без IP-адресов узла и без физических портов.

| Мост | Соединение |
|---|---|
| `vmbr0` | Внешняя сеть — ISP |
| `vmbr201` | ISP — HQ-RTR |
| `vmbr202` | ISP — BR-RTR |
| `vmbr203` | HQ-RTR — HQ-SW |
| `vmbr204` | HQ-SW — HQ-SRV |
| `vmbr205` | HQ-SW — HQ-CLI |
| `vmbr206` | BR-RTR — BR-FW |
| `vmbr207` | BR-FW — BR-SRV |
| `vmbr208` | Служебная карта HQ-RTR |
| `vmbr209` | Служебная карта BR-RTR |

Порядок адаптеров:

| ВМ | net0 | net1 | net2 |
|---|---|---|---|
| ISP | vmbr0 | vmbr201 | vmbr202 |
| HQ-RTR | vmbr208 | vmbr201 | vmbr203 |
| HQ-SW | vmbr203 | vmbr204 | vmbr205 |
| HQ-SRV | vmbr204 | — | — |
| HQ-CLI | vmbr205 | — | — |
| BR-RTR | vmbr209 | vmbr202 | vmbr206 |
| BR-FW | vmbr207 | vmbr206 | — |
| BR-SRV | vmbr207 | — | — |

На EcoRouter первая карта предназначена для управления, вторая подключена к ISP, третья — к локальной сети. На BR-FW первая карта подключена к BR-SRV, вторая — к BR-RTR.

Firewall на создаваемых адаптерах выключен. VLAN-теги Proxmox не назначаются. Сопоставление карт с интерфейсами гостевых ОС и настройка VLAN выполняются внутри машин после импорта.

## Источники образов

[Публичная папка Google Drive](https://drive.google.com/drive/folders/1ZkHbBdzr9-UAWuZ4TGUIs7O5DhCfvKmC)

| Файл | Использование |
|---|---|
| `alt-jeos.qcow2` | ISP и HQ-SW |
| `alt-server.qcow2` | HQ-SRV и BR-SRV |
| `alt-workstation.qcow2` | HQ-CLI |
| `EcoRouterOS.qcow2` | HQ-RTR и BR-RTR |
| `ideco.qcow2` | Основной диск BR-FW |
| `ideco-efi.qcow2` | Состояние UEFI BR-FW |
| `ideco-config.txt` | UUID SMBIOS и MAC net0 базовой Ideco |

ID файлов, имена и доступные контрольные суммы находятся в [`images.json`](images.json). Скрипт обращается к отдельным файлам, а не скачивает всю папку. Учётная запись Google для публичных файлов не требуется.

Файл конфигурации Ideco читается как данные: команды из него не выполняются. Основной диск и EFI должны быть экспортированы из одной выключенной ВМ. UUID SMBIOS и MAC net0 сохраняются, а CPU, RAM и подключения назначаются по параметрам скрипта. Лицензия после восстановления проверяется в панели Ideco. Оригинал и его копия с одинаковым MAC не должны одновременно подключаться к одной сети.

Для замены источников необходимо обновить `images.json` и проверить совместимость образов с контроллерами и прошивкой, которые задаёт `deploy.sh`. Замена только ссылки не гарантирует загрузку произвольной ОС.

## После развёртывания

Успешное завершение обозначается строкой:

```text
Finished: VM IDs 200–207. All machines are stopped.
```

При другом `--base-id` в сообщении будет соответствующий диапазон.

1. Проверить наличие восьми ВМ в панели Proxmox и их раздел **Hardware**.
2. Запустить машины по очереди, проверить загрузку ОС через **Console**.
3. Настроить уникальные имена внутри ОС, IP-адреса и необходимые службы.
4. Проверить лицензию Ideco и сопоставление её сетевых интерфейсов.

Название ВМ в панели не изменяет hostname внутри ОС. Пароли остаются такими, как в базовых образах; скрипт их не назначает и не сбрасывает. Данные для входа должны быть известны пользователю базового образа.

Копии общей ALT-базы наследуют системные идентификаторы и SSH host keys. Перед использованием им следует назначить уникальные machine-id и SSH-ключи узла. Автоматическая подготовка гостевых идентификаторов в текущей версии не реализована.

## Диагностика

Журнал каждого запуска сохраняется в `/root/demo-deploy.XXXXXXXX/deploy.log`. Там же находятся копия конфигурации сети до изменений, сведения о проверенных образах, расчёт места и список созданных ВМ, если создание уже началось.

### Недостаточно места

Сообщение `Not enough disk space` означает, что свободного места в целевом хранилище недостаточно для рассчитанного импорта и резерва.

Проверить состояние:

```bash
pvesm status
lvs -a -o lv_name,lv_size,data_percent,metadata_percent
```

Решения: расширить целевое хранилище или указать другое через `--storage`. Увеличение виртуального диска узла Proxmox само по себе не расширяет раздел, LVM и thin pool. Команды расширения зависят от фактической схемы дисков.

### Google Drive не отдаёт файл

В сообщении указываются имя файла и публичная ссылка. Возможные причины — изменение доступа, ограничение скачиваний Google или временная ошибка соединения. Доступность файла можно проверить в браузере без входа в аккаунт.

После устранения причины повторить:

```bash
bash /root/demo-bootstrap.sh --deploy
```

Завершённые скачивания сохраняются и проверяются перед повторным использованием; частичные скачивания возобновляются, если это поддерживается источником.

Для `ideco-efi.qcow2` в манифесте опубликованы размер и SHA256. Его можно скопировать вручную в каталог кэша с точным именем `ideco-efi.qcow2`; скрипт примет файл только при совпадении опубликованной контрольной суммы. Это также относится к другим файлам, если для них в манифесте задан SHA256.

Локальные контрольные суммы защищают от изменения кэша после скачивания. Они не являются подписью производителя ОС.

### Занятые VMID или мосты

Скрипт проверяет VMID по всему кластеру, включая контейнеры, и отказывается заменять существующие машины. Уже настроенные мосты нового диапазона также отклоняются. Для отдельного стенда следует выбрать свободные `--base-id` и `--bridge-base`.

### Ошибка после начала создания ВМ

Новые ВМ и сетевые изменения сохраняются для диагностики. Автоматическое удаление и откат не выполняются. Перед повторным запуском необходимо проверить журнал и состояние частично созданного стенда. Повторный запуск на уже занятый диапазон остановится; автоматическое продолжение частичного импорта не реализовано.

### Отложенные изменения сети Proxmox

При наличии `/etc/network/interfaces.new` запуск останавливается. Перед развёртыванием необходимо применить или отменить ожидающие изменения сети в Proxmox.

## Режим для существующих ВМ

Отдельный режим подключает адаптеры уже существующего стенда. Он использует [`connect-adapters.sh`](connect-adapters.sh) и [`machines.tsv`](machines.tsv), не скачивает образы и не создаёт машины.

```bash
bash /root/demo-bootstrap.sh --plan
bash /root/demo-bootstrap.sh --apply
```

`--plan` показывает изменения, `--apply` применяет их. **Эти параметры относятся к адаптерам существующих ВМ; для нового стенда используются `--deploy-plan` и `--deploy`.**

Перед применением необходимо проверить локальную таблицу `machines.tsv`, названия и номера ВМ, порядок карт и существующие мосты. ВМ должны быть штатно выключены, без блокировок и отложенных изменений; Suspend не заменяет выключение. Скрипт не выключает их автоматически.

При первой записи создаётся каталог `/root/demo-adapters-backup.XXXXXXXX` с конфигурациями и `restore-nics.sh` для возврата изменённых карт. Повторные запуски bootstrap сохраняют локальную таблицу VMID, чтобы не перезаписать пользовательские изменения.

## Статус проверки

Проверены синтаксис, формирование плана и 11 локальных тестов с имитацией команд Proxmox. Тесты охватывают импорт основного и EFI-диска, назначение ресурсов, отказ до изменений при занятых VMID и недостатке места, расчёт для thin pool, обработку ошибок Google Drive и проверку локальной копии по SHA256.

Полное развёртывание и загрузка всех предоставленных образов на реальном узле пока не подтверждены. При сообщении об ошибке следует приложить версию Proxmox, команду запуска, сообщение об ошибке и соответствующий фрагмент журнала без учётных данных.
